# Participants and session logging

Moved verbatim from CLAUDE.md (full original: docs/CLAUDE-full.md). CLAUDE.md keeps the short rules; this file has the detail.

## Screens
Bottom tab bar: **Review | Flashcard | Mock Quiz | Stats**. Gear icon in header opens **Settings** (which has **Sign out**); students never see a participant code. Lesson upload lives in **Admin** (Phase 6); the Review tab lists lessons only.

### Participants (Phase 6)
- The app is used by several students on one shared host over local Wi-Fi (`npm run study`: builds the client and the API server serves `client/dist` on one port; it prints the LAN addresses). Every student studies the same lessons.
- On open, students sign up or sign in (`AuthScreen.jsx`; `POST /api/auth/signup|login|logout`, `GET /api/auth/me`, `POST /api/auth/password`). The login session token is kept in the browser and sent as `Authorization: Bearer`. Students never type or see a participant code. Codes (normalised: `p7`, `P 7`, `P007` → `P07`; `P` + 1-3 digits) are the hidden study ID: sign-up gives the account the next unused code (while admin allows sign-ups), and admin, stats and the export still use it.
- Study IDs are handed out at sign-up (the next unused number; `last_study_number` in `settings` remembers the highest, so a withdrawn ID is never reused); there is no public list and no create route (`POST /api/admin/participants` and `GET /api/participants/:code` are gone). Migration 008 creates `P00` and gives it every record made before it (the researcher's test data).
- Every study request sends `Authorization: Bearer <token>`; the server (`server/src/middleware/participant.js`) answers 401 `auth_required` without a token and 401 `session_unknown` (or the revoked reason) for a token that is unknown or revoked, and the client then shows the sign-in screen again. No participant header is read any more: a study ID alone gets no access.
- **Accounts** (migration 018): `accounts` (email, scrypt password hash, lockout counters) belong to one participant; `auth_sessions` hold the SHA-256 of each login token, never the token. One live login per account (a unique partial index): signing in elsewhere asks first (409 `active_elsewhere`) when the other device was seen within `session_timeout_seconds` (Admin setting, 30-1800 s), then signs it out (`signed_out_elsewhere`). Repeated wrong passwords lock the account for a while (60 s, doubling up to 15 min). Admin > Accounts (`GET /api/admin/accounts`) shows each email next to its study ID and whether it is active, and can reset a password or sign an account out. Outside the database file and backups, that list is the only place emails and study IDs appear together.
- **For the teacher:** turn **Allow new sign-ups** off in Admin > AI and study settings once everyone is enrolled (otherwise anyone on the Wi-Fi who opens the app could create an account and take the next study ID). Emails are stored in the database, linked to study IDs only there and in backups; the research export never contains them. Treat backups and the `pre-restore-*.db` copy as identifying data.
- Shared by everyone: the teacher's lessons (and students' uploads once shared; see Student uploads), sections (and their cached rewrites), key points/terms, flashcards (the cards), `quiz_distractors`. Per participant: flashcard schedule (`flashcard_progress`), `flashcard_reviews`, daily new/review limits, quiz attempts and answers (resume, retake, previous best), review progress, sessions, events, stats.
- Withdrawal: `npm run participant:delete -- <email or study ID>` (`server/scripts/delete-participant.js`; students do not know their study ID, so an email works: it is looked up with `findAccountByEmail`) shows the rows per table (their `ai_calls`, own AI key, account and sign-in sessions included) and the email, asks you to type the study ID (`--yes` skips), deletes the participant row (everything cascades, the account and its sessions too), then `secure_delete` + `VACUUM` + `wal_checkpoint(TRUNCATE)` so nothing can be read back. The teacher's lessons stay; the participant's private uploads are deleted with it, shared uploads stay without an owner (see Student uploads).

### Session logging and events (Phase 6)
- A study session starts when a participant opens a lesson's Review (`reading`, any of its views), a flashcard deck (`flashcards`; the All lessons deck has lesson NULL) or the Mock Quiz (`quiz`). `client/src/lib/session.js` (pure, fake-clock tested) + `hooks/useStudySession.js`:
  - only active time counts: interactions are pointerdown, keydown, wheel, touchstart, scroll;
  - 5 min without interaction ends the session at the last interaction (`idle`; the idle minutes are not counted), the next interaction starts a new one;
  - `visibilitychange` hidden pauses the clock and sends the time at once (fetch keepalive); back within 5 min carries on, after longer the session ended when the app went away (`background`) and a new one starts;
  - heartbeat every 30 s (counting only up to the last interaction), `left` when the screen closes, `signed_out` on sign-out, `signed_out_elsewhere` when the account signs in on another device, `signed_out_by_admin` when the researcher signs it out or resets its password (migration 019; `switched` is only in old rows).
- Server (`server/src/sessions/store.js`): `active_ms` only grows and never exceeds the time since the start; a session with no report for 5 min reads as `unclosed`, ended at its last report.
- Live AI requests (`ai_calls`, written by the server): one row per rewrite request not served from the shared cache, with the source / provider / model that answered, fallback steps and reasons, `from_cache`, `saved_shared`, error code and time.
- Setting changes (`setting_events`, migration 011; the `events` table and its type list are untouched): one row per change of a setting a participant makes, `POST /api/setting-events { setting: 'motion', value: 'system'|'less'|'full' }` or `{ setting: 'theme', value: 'system'|'light'|'dark'|'ama'|'ama-dark' }` (`server/src/events/settings.js`, a zod enum per setting; a value of the other setting is a 400); logged by Settings only when the choice changes, never at startup (a device that never chose shows AMA with no row).
- Self-monitoring events (`events`): `stats_view` (the app, once per Stats open; never from the admin view), `quiz_retake` (the server, when a retake starts), `review_flashcards_tap` (quiz results link), `section_simplify` / `section_translate` (every tap that opens that rewrite, cached or not, with `section_index`).
- Every `study_date` uses the flashcard day: 04:00 Asia/Manila (`server/src/stats/days.js`, built on the scheduler's `studyDay`). A study week runs Monday 04:00 to Monday 04:00.
- Planning metric (`server/src/stats/planning.js`, pure): for each due review of a review-state card (learning steps don't count), the due day comes from the answer's `snapshot.due_at`: answered that study day `on_time`, later `late` with `days_late`; not answered after its due day `still_overdue`; due today and not done yet is not counted.
