# StudyRevr

Open-source, mobile-first study app. Students upload a lesson (.docx / .pptx / .pdf); an AI generates a sectioned review, flashcards (Anki-style spaced repetition), and mock quizzes. Built for a Practical Research 2 study comparing traditional studying vs AI-assisted studying, so study activity must be logged and exportable.

## Stack
- Backend: Node.js (LTS) + Express, ES modules
- DB: SQLite via better-sqlite3 (single file, migrations on startup)
- Parsing: mammoth (docx), officeparser + jszip (pptx), unpdf (pdf). Reject .doc/.ppt with a clear "save as docx/pptx" message. Scanned/image-only PDFs are accepted but flagged with a warning (no OCR).
- `raw_text` format: blocks separated by a blank line, one paragraph per line inside a block. A block is a pptx slide or a PDF page (a paragraph that runs over a page seam stays whole, in the page it starts on); for docx every paragraph is its own block. Word count and the low-text warning are computed on this final text.
  - pptx slide block: slide text (bullets as `- item`, numbered as `1. item`, table rows as `a | b`), then SmartArt text read from `ppt/diagrams`, then, when the `include_speaker_notes` setting is true (default; `settings` table, no UI until Phase 7), a line `Notes:` followed by the speaker notes. Slides are emitted in deck order.
  - pdf: lines repeating on most pages (headers/footers/page numbers) are stripped; wrapped lines are reflowed into paragraphs, `word-`/`next` line-end hyphens are joined (hyphen kept), inline `»`/`•` bullets get their own line, and a page that starts lowercase after an unterminated sentence is merged into the previous paragraph.
- Uploads: multer, 20 MB limit, extension + MIME check + file signature check (zip `PK` for docx/pptx, `%PDF` for pdf)
- Validation: zod for all AI JSON output and request bodies
- Frontend: React + Vite, Motion (`motion` package, formerly Framer Motion) for animations. Stats is drawn in CSS (no chart library).
- Single repo: `/server` and `/client`, root scripts to run both in dev
- Install: `npm ci` in the repo root only. `server/` and `client/` are npm workspaces with one root `package-lock.json` and `node_modules/`; `npm ci` inside `client/` (or `server/`) wipes the root `node_modules` and installs only that workspace. The lockfile's `libc` fields come from npm 11: installing with npm 10 drops them without any real change, so don't commit that churn. `overrides` pins `shell-quote` ^1.12.0 (concurrently pins a vulnerable 1.9.0).

## Conventions
- Plain JavaScript (no TypeScript) unless asked otherwise
- Keep files small and focused; one route file per feature
- No secrets in code; config via `.env` with a committed `.env.example`
- Mobile-first CSS, dark mode via `prefers-color-scheme` + manual toggle
- Look: a study journal (`client/src/styles/tokens.css`; mockups and the decision in `design/`). A plain page with a margin column (`--mw`, `--mgap` of 20px or more to the text) where the numbers that matter are written (`.mnote`, or a row that hangs into it, `.hang`). The margin's edge is a 1px neutral hairline (`--line`), drawn by `.main::before` only on pages whose margin holds numbers (see the `:has()` list in `shell.css`); an empty margin and the reader get no line, and nothing is red (`--margin` is only the logo's rule). Rules only under list rows; decks, flashcards and the end card are index cards (`--card-shadow`, `--r-lg` 2px; a deck shows two card edges under it, drawn in `--card-edge`); primary buttons are solid ink (`--ink-btn` / `--on-ink-btn`: navy in light, pale ink in dark), quiet buttons a ruled outline (`--ink-btn-press` is the primary button's pressed/hover colour). The edge of every control (quiet button, chip, option, rating button, upload zone) is `--control-border`, at least 3:1 against paper and sheet in both themes (light 3.9 on paper, 4.3 on sheet; dark 4.4 and 3.9; `--line-strong` stays for decorative rules). The pinned Previous/Next, Next question and flashcard answer bars have no frame: a paper background and one top hairline. On a wide screen the page and the desk behind it sit inside `--book-max` (84rem). Header, page and tab bar add `--safe-top/right/bottom/left` (device insets). There is one small radius, `--r-sm`. The highlighter is `.mk`: in light a marker stroke under the words (`--mk-top` 54%, the ink stays ink), in dark a bright marker over the word with dark text (`--mk-top` 10%, `--mk-ink`). Navigation is plain: the open tab is only its label highlighted (a bottom bar on a phone that respects `--safe-bottom`; from 56rem a quiet icon + label column beside the page). Learning counts use `--learn` (pencil amber), never red. The reader (`.lesson-view`) uses a slim 14px margin at every width so text and the quick check get the page (the section number is on the "3/8 sections" line); from 56rem the page is a sheet on the desk (`--desk`), and wide screens use two columns (decks beside All lessons, the quiz check and original text beside the reading, results beside the score, flashcards and quiz scores beside the week).
- Respect `prefers-reduced-motion` (skip non-essential animations), and the **Motion setting** (Settings › Appearance: Match my device (default) / Less motion / Full motion; `client/src/lib/motion.js`, kept like the theme: localStorage `studyrevr-motion` on this device, not per participant, written to `data-motion` on `<html>`). `useMotionReduced()` is the one source of truth for every animation (never `matchMedia` or motion's own `useReducedMotion`, which only know the device); `MotionConfig` gets `always` / `never` from it. CSS follows the same rule: `@media (prefers-reduced-motion) { :root:not([data-motion='full']) … }` plus `:root[data-motion='less'] …` (base.css, review.css). Less motion is exactly the reduced behaviour, Full the full one, Match follows the device live. It is visual only: the answer clock never reads it, so `time_ms` is the same with every choice (`client/test/clockScreens.test.js` runs every choice on a reducing and a full-motion device).
- Paper motion (`design/motion/`: the proposals and a static demo): things move like paper and pen, with transform / opacity only (plus `stroke-dashoffset` for pen strokes), each under ~600 ms (the deck coming out is the one exception), every one skippable by a tap and never blocking input; reduced motion: off or a plain fade. No new colours or radii: pen marks use `--accent` (the loop), `--ok` (the tick), `--ink-2` (the strike). Nothing a student sees is red: wrong answers, the "Again" rating and errors use `--ink-2` / `--learn` with an icon and a word; `--danger` is only for admin-only destructive buttons.
- **Answer time excludes animation and time away** (`client/src/lib/answerClock.js`, pure and fake-clock tested in `client/test/answerClock.test.js`; `hooks/useAnswerClock.js`): a flashcard's or quiz question's `time_ms` starts when it is on screen and usable (its entrance ended or was skipped, or at the first paint when there is none) or at the first tap or key if that comes sooner; the flip pauses it (reason `flip`) and so does the app being hidden (`visibilitychange`, reason `hidden`: the clock runs only while no reason is held, so a card finishing its turn in the background does not start it); a flashcard cannot be rated (buttons or keys 1-4) until `onTurned` (`canRate`; a 1.5 s fallback opens it if the end of the turn is never reported); the marks drawn after an answer play after it is recorded and never delay the next clock; a failed save reopens it. The same events give the same `time_ms` with reduced motion on or off. A reload restarts the open card's or question's clock at 0 (the codebook says so). The export codebook says rows answered before the study copy was updated to this version counted the animations of that time and did not pause when hidden (the researcher notes the day they update).
- Every AI call: strict "use only the provided lesson text" instruction, zod validation, one retry on invalid JSON, clear error surfaced to UI
- Provider errors become actionable messages (`server/src/ai/client.js`): 400 check the model in Settings (unless the body says the key is invalid, as Google's does: then the key), 401/403 check the API key in Settings, 404 model or base URL, 429 rate limited, try again shortly, timeout the provider is slow, retry. The provider's own error body is logged server-side with keys redacted and never shown in the UI.
- Every AI prompt that receives lesson text must explain that a `Notes:` line inside a slide block marks the teacher's spoken explanation of that slide: treat it as lesson content that elaborates the slide, not as a separate topic
- Long-running generation is async: create a job, frontend polls status

## AI Layer (provider-agnostic)
One adapter speaking the OpenAI-compatible `/v1/chat/completions` API. This covers Google Gemini, NVIDIA NIM, Ollama (`/v1`), llama.cpp server, OpenRouter, and similar.
- **Default provider: Google AI Studio** (Gemini, OpenAI-compatible endpoint, free tier ~15 requests/min). Key in `.env` as `GOOGLE_API_KEY`.
- **Presets** (`server/src/ai/providers.js`): `google` (default), `deepseek` (`api.deepseek.com/v1`, `DEEPSEEK_API_KEY`), `qwen` (DashScope international, `DASHSCOPE_API_KEY`), `nvidia-nim`, `openrouter`, `ollama`, `llamacpp`, plus `custom`. A preset is a base URL, default model, chunk tokens, concurrency, temperature (0.2), the `.env` key name and whether `response_format` json_schema is supported. Google: ~30000-token chunks, concurrency 2, json_schema on. The other presets keep small-model chunking (2400 tokens). Default model: `gemini-3.5-flash-lite` (id confirmed from Google's `/models`; a `models/` prefix is always stripped).
- **Model resolution order, per provider:** one-off request value (e.g. test-ai body) > Settings (`settings` table) > `.env` (`AI_MODEL`) > preset default. The model is never fixed: `GET /api/settings/models` lists the provider's chat models (embedding, image, video, TTS, live/audio, ASR, rerank, `aqa`, `deep-research-*`, `antigravity-*`, `*computer-use*`, `nano-banana*`, `*-customtools`, `gemini-omni-*`, Qwen's wan/wanx/cosyvoice/paraformer/sambert etc. are filtered out, `server/src/ai/models.js`) and a free-text model id is always accepted if `/models` fails or is empty. The active provider and each provider's last model are saved separately (`ai_provider`, `ai_model:<provider>`), so switching providers restores that provider's model.
- **Keys are per provider:** `GOOGLE_API_KEY`, `NVIDIA_API_KEY`, `OPENROUTER_API_KEY` in `.env`, or saved in Settings (`ai_api_key:<provider>`). Only the active provider's key is ever sent. The API returns only a "key set: yes/no" flag; keys are never logged or returned, and a backup export must exclude `ai_api_key:*`. The SQLite file holds saved keys, so it is git-ignored. Every way a key is deleted (Remove my key, Delete all student keys, replacing a key, `participant:delete`) turns on `secure_delete` and then runs `wal_checkpoint(TRUNCATE)` (`wipeDeletedKeys` in `services/student-ai.js`): in WAL mode the old page stays readable in the `-wal` file until a checkpoint, so `test/student-key-wipe.test.js` scans the db and `-wal` files for the key afterwards.
- Optional `.env` overrides `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL`, `AI_EXTRA_BODY` (JSON merged into the request body, zod-validated, ignored if invalid) apply only to the `.env` provider (`AI_PROVIDER`). Tuning: `AI_CONCURRENCY`, `AI_CHUNK_TOKENS`, `AI_TEMPERATURE`, `KEY_TERMS_MAX`.
- Calls within one pipeline stage run in parallel up to the concurrency limit; stages stay in order (sections, key points, key terms, flashcards, quiz options). 429/5xx/network errors retry with growing, jittered waits (Retry-After honored: header in seconds or a date, or Google's `retryDelay` in the body; at most 60 s). Request timeout is a preset value (`AI_TIMEOUT_SECONDS` overrides): Google 60 s, every other preset 300 s; a timed-out request is retried once. The reply body is read inside the timed attempt, so a stalled body is a timeout too.
- **Per-model tuning** (preset `models`): `{ timeoutMs, requestsPerMinute, extraBody }` replace the preset's for that model id (`extraBody` is merged into that model's requests, under `AI_EXTRA_BODY`). Google `gemini-3.5-flash-lite`: 25 s timeout, 15 requests/min. `gemma-4-26b-a4b-it` (the live fallback): 25 s, 30 requests/min, `reasoning_effort: "minimal"` (Gemma refuses "none"/"low"; without it it thinks for 25-30 s and can spend all of max_tokens; measured with it: Explain simpler 4.7-5.9 s, Taglish 9.4-12 s). `gemma-4-31b-it`: 60 s (measured 33-50 s), same options. `requestsPerMinute` is a client-side limit per host + model + key (`server/src/ai/ratelimit.js`) that every HTTP attempt takes a slot from, retries included; under it, a 429's Retry-After holds every call to that model.
- **Attempt log:** the client reports every HTTP attempt to `onAttempt` (`throttle` / `start` / `ok` / `fail`, failure reason `timeout` | `rate_limit` | `server` | `network` | `http_<status>`). The server logs each as `[ai] ...`, `npm run pipeline` prints them with times, and `stats` counts attempts, failures and retries by reason (timeouts included). `npm run pipeline` also wraps the process's `fetch` (`server/src/ai/netlog.js`) to log and count every HTTP request from any code and flags a mismatch with the client's count, reports event-loop stalls, and the flashcards stage logs its time split (AI calls / checks and de-duplication / saving).
- **Grounded key terms:** each key term comes with an `evidence` quote (at most 25 words) copied from the lesson. In code the quote must exist in the lesson text (case, spacing, punctuation and line-end hyphens ignored) and must say more than the term or a title; otherwise the term is dropped and logged. Evidence is stored in `key_terms.evidence` for the Review UI. Key terms are domain concepts only (no list-item examples or evaluative phrases), de-duplicated across chunks (case- and plural-insensitive, in code), at most `KEY_TERMS_MAX` (12) per lesson.
- **Key-terms merge:** a lesson split into several chunks gets one extra call (`the merged key terms`) after the per-chunk calls. It receives every candidate term with its definition/evidence versions and returns only candidate numbers (and which version): it can drop evaluative phrases, examples, weak terms and synonyms and pick the best version, but cannot add terms or write evidence. The grounding check runs again afterwards against the whole lesson. An unusable reply keeps all candidates (capped) rather than erasing the terms. Single-chunk lessons skip the call.
- **Live calls** (Explain simpler, Filipino/Taglish; `server/src/ai/live.js`, `server/src/services/live-rewrite.js`): a fallback chain, one try per step (`live: true`: no HTTP retry waits, no timeout retry, and a request that would wait over 3 s for the client-side limit fails at once as a rate limit; a real 429 pauses the limiter for that model for its Retry-After, so later live calls skip straight to the next step): the student's own key (when admin allows it and they saved one) → the admin Default → `GEMMA_MODEL` (`gemma-4-26b-a4b-it`) on the admin's Google key (skipped without a Google key or when Default is that model) → error "The AI is busy, try again in a minute." (rate limit) / "The AI couldn’t answer right now. Try again in a minute." (every other failure: outage, retired model, rejected key, unusable reply) with Try again. **Students never see a provider message or a pointer to Settings** (`finalError` in `live-rewrite.js`); the real reason is in `ai_calls.error_code` / `fallback_reasons` and admin sees it (see Admin, `GET /api/admin/ai-problems`). Every step falls back on `rate_limit`, `timeout`, `network`, `provider_error` (5xx); Default and Gemma also on `invalid_json` / `bad_response` (the model gave nothing usable); the Default also on `not_found` and `bad_request` (a retired or mistyped Default model, which some providers answer with 400: Gemma is a different model and still answers, with the "backup AI" note); the student step also on `auth` (401/403), `no_credit` (402), `not_found` and `bad_request` (a retired or unsuitable model: Default is another model). A rejected key, no credit or a missing key/model on the Default does not fall back (Gemma uses the same admin key); the student sees the plain "couldn’t answer" message and admin sees the reason. `ai_calls.fallback_steps` is how many times the request moved on to the next step: the failed steps before the answer, or, when nothing answered, the steps tried after the first (a rejected key on the Default alone is 0; Default then Gemma both failing is 1). The student's timeout is 25 s like the other steps. The routes need a participant code (`requireParticipant`): no code, no AI call. Gemma is limited to 8 requests a minute (its 16K tokens a minute are the real limit), retries once at once on a provider 5xx only (not a timeout; logged as `gemma:provider_error` in `fallback_reasons`), and taps on the same section and kind while it answers share one Gemma call (`coalesce` in `live-rewrite.js`, like the Default's; its answer is still never cached). Gemma gets only the section and capped answers (`SMALL_MAX_TOKENS`: 1200 simplify, 2000 translate); the system message works with Gemma (no need to move it into the user message); its `<thought>…</thought>` blocks are stripped before JSON parsing (`server/src/ai/json.js`). Only Default answers become the shared cached version (`saveSharedVersion`, first one wins, with `*_made_by`); student-key and Gemma answers are returned to that student only and not stored. Only the request that stored the Default's version has `saved_shared = 1`; a tap that joined it, or one that finished after Prepare (or another tap) saved a version, shows the stored shared version (so everyone reads the same text) and logs `from_cache = 1`. A student with a saved key always gets a live call from their key; without one, a cached shared version is served with no AI call. A response carries `answered_by` and `fallback: { steps, note }`; the client shows the note under the rewrite ("Your key didn’t work, so the default AI answered." / "The main AI was busy, so a backup AI answered." / "Your key didn’t work and the main AI was busy, so a backup AI answered."). Every live request writes an `ai_calls` row and an `[ai-live]` log line. Lesson processing never uses the chain, a student key or Gemma.
- Interface: `generateJSON({ system, user, schema })` → validated object
- Separate calls per feature (sections/summary, key terms, flashcards, quiz). Never one giant call.
- Chunk long lessons by paragraph (one line of `raw_text` = one paragraph), packing paragraphs up to the token budget so small local models (~8k context) work. Slide/page blocks and headings are soft boundaries: prefer to cut between blocks, never split a paragraph, and keep a slide's `Notes:` with its slide where it fits.
- Request JSON only; strip code fences before parsing

## Screens
Bottom tab bar: **Review | Flashcard | Mock Quiz | Stats**. Gear icon in header opens **Settings**; beside it a chip shows the participant code in use. Lesson upload lives in **Admin** (Phase 6); the Review tab lists lessons only.

### Participants (Phase 6)
- The app is used by several students on one shared host over local Wi-Fi (`npm run study`: builds the client and the API server serves `client/dist` on one port; it prints the LAN addresses). Every student studies the same lessons.
- On open, a code screen (`ParticipantScreen.jsx`, type-only: no list, no suggestions, P00 never shown) asks for a participant code. `GET /api/participants/:code` checks it; an unknown code shows "That code isn't on the list. Check with your teacher." Codes are normalised (`p7`, `P 7`, `P007` → `P07`; `P` + 1-3 digits). The code is kept in localStorage until **Settings › Switch participant**.
- Codes are created only in admin (`POST /api/admin/participants { codes: "P01-P10, P12" }`); there is no public list or create route. Migration 008 creates `P00` and gives it every record made before it (the researcher's test data).
- Every study request sends `X-Participant`; the server (`server/src/middleware/participant.js`) answers 401 `participant_required` / `participant_unknown` without a listed code, and the client then shows the code screen again.
- Shared by everyone: lessons, sections (and their cached rewrites), key points/terms, flashcards (the cards), `quiz_distractors`. Per participant: flashcard schedule (`flashcard_progress`), `flashcard_reviews`, daily new/review limits, quiz attempts and answers (resume, retake, previous best), review progress, sessions, events, stats.
- Withdrawal: `npm run participant:delete -- P07` (`server/scripts/delete-participant.js`) shows the rows per table (their `ai_calls` and own AI key included), asks for the code again (`--yes` skips), deletes the participant row (everything cascades), then `secure_delete` + `VACUUM` + `wal_checkpoint(TRUNCATE)` so nothing can be read back. Lessons stay.

### Session logging and events (Phase 6)
- A study session starts when a participant opens a lesson's Review (`reading`, any of its views), a flashcard deck (`flashcards`; the All lessons deck has lesson NULL) or the Mock Quiz (`quiz`). `client/src/lib/session.js` (pure, fake-clock tested) + `hooks/useStudySession.js`:
  - only active time counts: interactions are pointerdown, keydown, wheel, touchstart, scroll;
  - 5 min without interaction ends the session at the last interaction (`idle`; the idle minutes are not counted), the next interaction starts a new one;
  - `visibilitychange` hidden pauses the clock and sends the time at once (fetch keepalive); back within 5 min carries on, after longer the session ended when the app went away (`background`) and a new one starts;
  - heartbeat every 30 s (counting only up to the last interaction), `left` when the screen closes, `switched` on Switch participant.
- Server (`server/src/sessions/store.js`): `active_ms` only grows and never exceeds the time since the start; a session with no report for 5 min reads as `unclosed`, ended at its last report.
- Live AI requests (`ai_calls`, written by the server): one row per rewrite request not served from the shared cache, with the source / provider / model that answered, fallback steps and reasons, `from_cache`, `saved_shared`, error code and time.
- Setting changes (`setting_events`, migration 011; the `events` table and its type list are untouched): one row per change of a setting a participant makes, `POST /api/setting-events { setting: 'motion', value: 'system'|'less'|'full' }` (`server/src/events/settings.js`, a zod enum per setting so `theme` can be added later); logged by Settings only when the choice changes, never at startup.
- Self-monitoring events (`events`): `stats_view` (the app, once per Stats open; never from the admin view), `quiz_retake` (the server, when a retake starts), `review_flashcards_tap` (quiz results link), `section_simplify` / `section_translate` (every tap that opens that rewrite, cached or not, with `section_index`).
- Every `study_date` uses the flashcard day: 04:00 Asia/Manila (`server/src/stats/days.js`, built on the scheduler's `studyDay`). A study week runs Monday 04:00 to Monday 04:00.
- Planning metric (`server/src/stats/planning.js`, pure): for each due review of a review-state card (learning steps don't count), the due day comes from the answer's `snapshot.due_at`: answered that study day `on_time`, later `late` with `days_late`; not answered after its due day `still_overdue`; due today and not done yet is not counted.

### Admin (Phase 6)
- `#/admin`, reached from a quiet link under the card on the code screen (not from Settings: students don't need it). Phase 7A sections after Research export: **AI and study settings** (Default AI: provider, key set / not set, chat-model picker with free text when the list fails, Test connection, Save; New flashcards per day; switch "Allow students to use their own API key", default off; **Delete all student keys** with a confirmation, `DELETE /api/admin/student-keys`, for after the study; above the form, a warning for each Default problem settings can fix seen in the last 24 hours — model not found, key rejected, no credit, bad request, not set up — with how many requests the backup AI answered and how many got "try again": `GET /api/admin/ai-problems`, `server/src/services/ai-problems.js`, read from `ai_calls`) and **Backup** ("Download backup", "Last backup: …"). `ADMIN_PIN` in `.env` (empty: admin off, 403 `admin_off` everywhere). The client sends `X-Admin-Pin` (kept in sessionStorage after `POST /api/admin/unlock` accepts it); the server compares digests in constant time (`server/src/middleware/admin.js`); missing/wrong PIN 401 `admin_pin`; 5 wrong PINs from one address lock it for 60 s (429).
- Behind the PIN: everything under `/api/admin`, plus upload / retry / delete of lessons, `POST /api/lessons/:id/flashcards/generate`, and all of `/api/settings/*`. Section rewrites and the quiz's fallback wrong-answer call stay open (studying).
- Screen: **Participants** (add codes; summary table; a code opens `#/admin/participants/P03`, that participant's StatsView), **Research export**, **Lessons** (upload zone, list with delete; retry on the lesson's processing page; per lesson a quiz-answers retry button when that step failed or was never made, and the **Prepare simpler and Taglish** step with its status).
- **Prepare** (`POST /api/lessons/:id/section-versions`, admin; `server/src/services/prepare-versions.js`): an on-demand job stage `section_versions` (`ON_DEMAND_STAGES` in `pipeline/jobs.js`: a job queued there runs only that stage and never fails the lesson) that makes every missing shared Explain simpler / Filipino-Taglish version with the Default through the pipeline client (its 15/min limit, retries, concurrency), saving each as it is made; a retry makes only the rest. `GET /api/lessons` rows carry `section_versions: { missing, total, status, error, progress }`. Taps still log `section_simplify` / `section_translate` events as before.
- **Backup** (`GET /api/admin/backup`, `server/src/services/backup.js`): better-sqlite3 `backup()` into a temp file `backup-tmp-<uuid>.db` next to the database (never the system temp folder; removed in a `finally`, leftovers removed at server start), then on the copy: journal mode DELETE, `secure_delete`, delete `settings` `ai_api_key:*` and all `participant_ai_keys`, VACUUM; sent as `studyrevr-backup-YYYY-MM-DD-HHMM.db` (Asia/Manila) and logged in `admin_events` (`GET /api/admin/backup/last`). The PIN is only in `.env`. **Restore**: `npm run restore -- <file>` (`server/scripts/restore.js`; a relative path is from where you typed it, via `INIT_CWD`): refuses while a server runs (the server writes `<db>.pid` on start and removes it on exit; also pings `/api/health` on `PORT`), checks integrity / StudyRevr tables / no unknown migrations, asks to type `RESTORE`, saves `pre-restore-<time>.db` beside the database (it still holds the keys: the script says to delete it once the restore checks out; a stale pid file message says which file to delete), swaps the file in (removing `-wal`/`-shm`), runs migrations, and prints a reminder to re-enter the API key and check `ADMIN_PIN`. Students see no upload, delete, retry or Make cards ("Cards aren't ready yet").
- **Cards that give their answer away** (admin's list, `GET /api/lessons?counts=1`, rows carry `leaks: { cards }`: cards breaking g, i, j or k (`CARD_LEAK_RULES`); h is not counted, the quiz blanks the term; `GET /api/admin/lessons/:id/leaks` is `lessonLeakReport` in `server/src/quiz/check.js` (h cards listed apart as `names_term`) plus `can_regenerate` and `regenerate_blocked` (`lesson_has_records` | `lesson_busy` | null)): the admin lesson row says "N flashcards give the answer away." with **Show cards** (`LeakyCards.jsx`), each card with the rules in plain words and **Regenerate this card** (`POST /api/admin/flashcards/:id/regenerate`, `server/src/services/regenerate-card.js`): one Default-AI call (`regenerateCardPrompt`) with the card, why it was flagged, the lesson block around its evidence and (concept cards) the other cards' answers; a concept card gets a new question, answer and evidence (checked like generation), a term card a new definition (at least half of its content words must be lesson words). Still leaking, too long, a quote not in the lesson, a definition not from the lesson, or a repeat of another card (`isDuplicate` in `pipeline/flashcards.js`, and no other card with the same answer): 422 `card_not_better`, nothing saved. Otherwise the card is updated **in place** (same id, so old `quiz_answers` rows still point to it; P00's schedule is kept) and its `quiz_distractors` row deleted, so "Make quiz answers" remakes them. Blocked with 409 `lesson_has_records` once a participant other than P00 has records on the lesson (`participantRecords` in `server/src/services/lesson-records.js`, shared with lesson delete); the list then says the cards can't change. Also refused with 409 `lesson_busy` while the lesson is not ready or any job is queued or running on it (processing, quiz answers, Prepare, making cards) (`regenerateBlock`). Both are checked again inside the save transaction after the AI call, together with the card's text (changed meanwhile: 409 `card_changed`), so a participant who started during the call blocks the save.
- **`npm run quiz:check`** (`server/scripts/quiz-check.js`; `-- --lesson <id>`, `-- --db <file>`, a relative path from where you typed it): opens the database read-only (safe beside a running server; works on any StudyRevr database), no AI or key, and prints per lesson the flashcards flagged by g-k, the multiple-choice questions and Yes/No false statements possible / clean / skipped by rule with up to 5 examples, the term definitions shown blanked, the cards the quiz never asks, and **"Clean questions available: N of 10"** (run it before the study to confirm the study lesson fills a full quiz).
- **Lesson delete is blocked** (409 `lesson_has_records`, `records` counts in the body) once a participant other than P00 has flashcard answers, quiz attempts/answers, study sessions or events on the lesson. The message says what deleting would do: remove their flashcard answers and quiz attempts (with answers), and cut their sessions and events off from the lesson (those rows stay, `lesson_id` goes NULL). P00 records do not count and go with the lesson. There is no override: a lesson becomes deletable only when those records are gone.

### Flashcard (Anki-style)
- Row per lesson: name | Start | New / Learning / Due counts
- Study screen: front → tap to flip → Again / Hard / Good / Easy
- SM-2 scheduling. User-configurable: new cards/day (20), max reviews/day (200), learning steps (1m 10m).
- Defaults (code, each overridable by a `settings` row; see `server/src/flashcards/config.js`): graduating interval 1d, easy interval 4d, starting ease 2.50, easy bonus 1.30, hard interval 1.20, relearning step 10m, lapse new interval 0 (then min 1d), min interval 1d, max interval 36500d
- The study day starts at 04:00 Asia/Manila. Daily limits are one budget across all lessons ("All lessons" is the parent deck). Queue order: due (re)learning cards, due reviews, new cards (lesson order); learn ahead 20 min when nothing else is left.
- **Early-review guard** (`recordAnswer` in `server/src/flashcards/study.js`): an answer to a review-state card whose `due_at` is on or after the end of the current study day (the queue's own rule) is refused with 409 `not_due` (with `due_at`), so nothing is saved; learning and new cards are unaffected. The study screen never offers such a card; if it gets `not_due` (the card was answered in another tab) it quietly reloads the deck.
- **New-card limit guard** (same function): an answer to a new card when the participant has already answered `newPerDay` new cards this study day (`doneToday`, one budget across all lessons) is refused with 409 `new_limit` (with `new_per_day`), nothing saved. The queue never offers a new card beyond the limit, so the study screen is unchanged; on `new_limit` (another tab used up the day) it reloads the deck like `not_due`. Undo removes the answer from `doneToday`, so an undone new card can be answered again. Review answers (`maxReviews`) are not guarded.
- Intervals are fuzzed like Anki (±25/15/5%), from a seeded generator (seed = card id + reps), so the interval on a button is exactly what the card gets and tests are deterministic. The scheduler (`server/src/flashcards/scheduler.js`) is pure: it takes `now` and the config.
- Card generation is the pipeline's `flashcards` stage (also `POST /api/lessons/:id/flashcards/generate` for a lesson with no cards; the lesson stays ready while it runs). Term cards come from the grounded key terms; concept Q → A cards come from one AI call per chunk (the chunk's review sections as a guide). Every card has an `evidence` quote checked in code like key terms; answers over 40 words (prompt asks ≤ 25) are dropped; a concept card that gives its answer away is dropped (`cardLeaks` in `quiz/leaks.js`: **g** the front holds the back or 80% of its content words, **i** a yes/no or either/or question (English auxiliaries first, `o hindi`, `or not`, or `ba` in a question with no question word: "Ano ba…", "Bakit ba…" still ask what / why; a plain Filipino `o` is not one), **k** the back only restates the front (content-word overlap 0.8 or more, so "Bakit mahalaga…" → "Mahalaga … dahil …" is kept); after de-duplication, **j** a front that holds another card's answer). The prompt asks for no answer words in the question, no word that already means the answer, no yes/no or either/or questions, and an answer that says more than the question. Rule **h** (a term card's definition holds the term: both words of a one- or two-word term, as whole words or stems, or more than half of a longer one, so "cell" alone is not "Cell membrane") is information only, never dropped, counted as a leak or offered for Regenerate (`npm run quiz:check` prints it on an "Info:" line): the key-terms prompt forbids it and the quiz blanks the term; cards are de-duplicated against each other (term cards win). About one card per 50 words, at least 5, at most `flashcards_max` (30); term cards take at most half.
- Motion (`StudyScreen.jsx`, `DeckShuffle.jsx`, `FlipCard.jsx`, `lib/paper.js`): each time a deck starts, "Getting your deck out" with 3 or 4 random riffles (`shufflePlan`, about 0.6 s each, 1.8-2.4 s; tap, Enter, Space or Esc skips; a 450 ms fade under reduced motion; never "Shuffling": the queue order is fixed). The card sits on a deck (two `--card-edge` edges under it). The flip is a paper turn (3D rotateY with a fold shadow and a 4 px lift; cross-fade under reduced motion). After an answer, a ghost of the card goes back into the deck when its button comes back today (`comesBackToday`: minutes under a day) or onto a small done pile in the margin (its count written as an `.mnote`), and the pile squares up above the done card; undo plays it back out. Space flips, 1-4 answer, U / Ctrl+Z undo (multi-level within a session). "From the lesson: …" evidence under the answer. Done state says when the next card is due.

### Mock Quiz
- Row per lesson: name | Start | best finished score and number of attempts (`GET /api/quiz`). Lessons still preparing, without flashcards, or with only one card say why instead of Start.
- Questions come from the lesson's existing flashcards (no new grounding), built in code when a quiz starts (`server/src/quiz/build.js`, pure, seeded `random` in tests): up to 10 questions, one per card, cards picked at random; fewer if the lesson has fewer usable cards ("This lesson supports 6 questions"). A quiz needs at least 2 cards.
  - **Term card**: multiple choice "which term matches this definition?"; the 3 wrong options are other key terms of the same lesson (term cards, then `key_terms` without a card; plural-insensitive), no AI call. Fewer than 3 other terms: true / false against **another term card's definition only** (never a concept card's answer, which is plainly not a definition); with no other term card the card is not asked. A definition that holds its own term (or a form of it) is shown with the term blanked as `___` (`maskTerm`, which blanks every form `termInText` finds); the blanked text is checked again and a definition that still shows its term is neither asked nor used as another term's false statement; the stored `answer_text` and the card are unchanged.
  - **Concept card**: multiple choice with 3 AI-made wrong answers. Without 3 clean ones: true / false, whose false statement is one of the card's own saved wrong answers that passes the checks or, with none saved, another concept card's answer on the same subject (sharing a content word with the question).
  - **Leak checks** (`server/src/quiz/leaks.js`, pure, English and Filipino/Taglish: stopwords of both, a light Filipino stemmer for the linker, prefixes, `-um-`/`-in-`, reduplication and suffixes, English plurals and -ing/-ed; each text is stemmed by its own language, and a short phrase whose language `language()` can't tell is compared under both stemmers, a match under either counting; the lesson's words for the off-topic check hold both stems of every word and are cached by the lesson text, `lessonWords`): nothing that gives its answer away is asked. Rules: **a** the question holds the answer or 80% of its content words (a one-word answer only as a whole word or stem: "Cell" is not in "excellent", "Data" not in "database"); **b** two or more words of the question that only the right option repeats, as the same word or stem ("data" is not "database"), leaving out the question's topic (its word the lesson uses most, such as `wika` or "plants"), so one echoed word never flags; **c** the right option stands out (length outside 0.6-1.6x and more than 4 words apart, the only full sentence, every wrong option opens with the same 2 words, or tone: the wrong ones are negative or reversed beside a positive right answer, or the right answer is the only negative one. Negatives are whole words: `hindi`, `wala`, `not`, `never`, English reversing verbs in their inflected forms (`prevent(s/ed/ing)`, `hide(s)`, `hiding`, `remove`, `harm(ful)`...; not `hidden`, `harmony`, `blockchain`, nor `reduce` / `decrease`, which only describe an amount), Filipino reversing stems compared exactly (`pigil`, `tigil`, `bura`, `hadlang`, `wala`...; not `burador`), and `mahirapan`, `alisin`, `itago` only in those verb forms (`paghihirap`, `pag-alis`, `nakatago` are topic words); `bawas` no longer counts; "No. 7" / "(no.)" is the number sign); **d** a term question's definition holds the term; **e** a Yes/No false statement that is false from its wording (negative, another language, another kind of card's answer, another subject, another concept card's answer when it is a saved wrong answer) or that is the right answer's own words (reworded, so maybe true, or reversed); a term question's false statements (other term cards' definitions) also go through it, and never name the asked term; **f** wrong options that are near-duplicates of each other (content-word overlap 0.7 or more), the right answer's own words (a second right answer, or a swapped / reversed copy), another concept card's answer (it plainly answers that other question, so a student matches it away), in another language, or about nothing in the lesson. `quizCandidates` in `build.js` keeps only clean forms per card (multiple choice first, then Yes/No, else the card is skipped), so a lesson that can't fill 10 clean questions gets fewer ("This lesson supports N questions"); `usableCount` (the Mock Quiz tab's number) uses the same filter with the saved wrong answers and the lesson text. These are word checks: a question whose *meaning* gives the answer ("Why is language called dynamic?" -> "it changes"), a wrong option reversed in meaning without a negative word, or a synonym of the right answer ("pagbabahagi" for "share") is left to the prompts and the admin flag.
  - About 3 in 10 questions are true / false (choices `True` / `False`) for variety even when every card could be multiple choice. Multiple-choice options are shuffled silently.
- **Wrong answers** (`server/src/quiz/distractors.js`): made as the last step of lesson processing (the pipeline's `quiz_options` stage, after flashcards; the lesson stays `processing` until it ends, so students never wait on the AI when starting a quiz). The AI is asked (existing adapter, rate limiter, zod, one JSON retry) for 3 wrong answers per concept card, in batches of at most 15 cards so each call stays under the 25 s timeout; batches run up to the provider's concurrency. The prompt gets each card's question, answer, evidence quote, word count and language, uses only that lesson content, explains `Notes:`, and asks for wrong answers that directly answer **this** question and are the same kind of thing it asks for (a condition for "Kailan…", a list of the same category for "Anong uri…"), never another card's answer, on the question's subject, similar in length and style to the correct one, **in the same tone and polarity** (no negations, opposites or "hides / prevents / limits" versions; it no longer asks to "reverse a relationship", which made the right answer the only positive option), echoing the question's words when the right answer does. In code, wrong answers that match the correct answer or each other (case-insensitive, trimmed), run over 40 words, or break rule c (tone, length) or f (language, off-topic, the right answer's own words, another card's answer) are dropped, and the 3 kept must pass b / c / f as a set (`pickWrongSet`). A card left without a clean set gets **one** follow-up call (label `the quiz answer options (second try)`) listing the kept answers and the rejected ones with why; whatever is clean then is saved (fewer than 3: the card is asked as Yes/No), and a set still not clean after that call is **settled** (`quiz_distractors.settled = 1`, migration 010): no remake or lesson retry asks the AI for it again (a failed follow-up call does not settle it; regenerating the card deletes the row). Saved in `quiz_distractors` and reused; a batch that fails is not saved. **Failure of this stage does not fail the lesson:** the job records `quiz_options` / `failed` with the message, the lesson is `ready`, and admin gets a retry button (`POST /api/lessons/:id/quiz-options`, also used to fill in lessons made before the stage existed and to remake saved sets that give the answer away; only those cards are asked for). No wrong answers are made for a card that can never be multiple choice (its question gives the answer away, rule a or k). A set is saved only if the card's question and answer are still the ones it was made for (a card regenerated during the call is asked for again). The stage and the retry use `includeFailing` (`cardsNeedingDistractors`): cards with no saved row plus cards whose saved set the quiz can't use (not cards whose own question gives the answer away, nor settled sets), so the stage converges. Admin's list (`GET /api/lessons?counts=1`) rows carry `quiz_options.missing` (none saved) and `quiz_options.weak` (saved but leaking, not settled, and the card's own question doesn't give the answer: what a remake can still fix; the admin row then says "N quiz questions are skipped or changed to keep answers hidden." with **Remake quiz answers**). **Fallback:** starting a quiz still calls `ensureDistractors` for any card without them (never for a saved set that leaks: the builder just leaves it out), so the quiz starts either way (with a notice and true / false questions if that fails too). `ensureDistractors` is shared per lesson: the stage, a retry and quiz starts that overlap wait for one AI call (an `includeFailing` call that finds a missing-only run waits for it, then runs its own).
- Untimed. Time per question (`time_ms`, capped at 1 h) and total time (`duration_ms`) are recorded. Quiz results never touch flashcard scheduling or `flashcard_reviews`.
- Screen (`#/quiz/:lessonId`): "Getting your quiz ready" (after 2.5 s: "The AI is thinking up answer options…"), then the test sheet is handed out (slides up 32 px and fades in, 420 ms; a tap, Enter, Space or Esc skips; a fade under reduced motion), then one question at a time with no wait between them (no exit animation: the next question is the only one on the sheet), the progress as answer-sheet bubbles (`AnswerSheet`, `bubbleStates` in `lib/quiz.js`: answered filled, current a ring, neutral only; `role="progressbar"`). After an answer is saved it is marked in pen (`Pen.jsx`): a loop drawn round the chosen option's number, a tick on the right option, a strike through a wrong chosen one (one-line options only); a tap finishes them and Next never waits. The results' score is circled like a grade. After each answer: correct / not quite, the right answer and the card's "From the lesson: …" evidence; Next sits in the pinned action bar. Keys: 1-4 answer (1-2 on true / false), Enter next. A true / false question is **shown as Yes / No** (`yesNoAsk` / `yesNo` in `client/src/lib/quiz.js`; kicker "Yes or no?"): a term card asks "Does this describe **[term]**?", a concept card "Is this the right answer to **[question]**?", the statement quoted under it, buttons Yes / No. The results list ("Missed questions": the question, "Your answer", "Right answer" as Yes, or No plus the real answer) uses the same wording. It is display only: `choices`, `chosen_answer`, `right_answer` and the export stay True / False, and the codebook says so. Focus moves to each new question, then to Next (described by the feedback), then to the results heading.
- Results: score, percent, time, comparison with the best earlier score, the missed questions (your answer, right answer, evidence), **Retake** (same questions, new question order and option order, shuffle again) and **Back to lesson**. The Flashcards done card's main action is "Take the mock quiz".
- Tables (migration 007):
  - `quiz_distractors` (flashcard_id PK → flashcards ON DELETE CASCADE, choices JSON of 0-3 wrong answers, made_at, `settled` 0/1 (migration 010; `npm run quiz:check` never reads it, so it works on older databases))
  - `quiz_attempts` gains `started_at`, `finished_at` (NULL for a quiz left part-way), `duration_ms`, `retake_of` (the attempt whose questions it reused; NULL for a fresh quiz). `score` is final once finished.
  - `quiz_answers` (id, attempt_id → quiz_attempts ON DELETE CASCADE, position, flashcard_id ON DELETE SET NULL, type `mc`|`tf`, kind `term`|`concept`, question, statement (tf), choices JSON, answer_index, answer_text, evidence, chosen_index, correct, time_ms, answered_at): one row per question, written at start and filled in when answered; a full copy, so it outlives card changes. Phase 6 reads it.
  - `quiz_questions` (001) is unused: questions are built from flashcards per attempt.
- **Resume:** `POST /api/lessons/:id/quiz/attempts` without `retake_of` returns the lesson's newest unfinished attempt if it started less than 2 hours ago (200, `resumed: true`, `next_position` = first unanswered question or `null` when all are answered, `elapsed_ms` = time already spent), so a reload or coming back never creates a second attempt. Older unfinished attempts are left as they are (abandoned). A retake always starts a new attempt. The results screen offers "Review these flashcards", a plain link to the lesson's flashcard deck; it changes no scheduling.
- Endpoints: `GET /api/quiz` · `POST /api/lessons/:id/quiz/attempts` (body `{ retake_of? }`; returns questions without answers) · `POST /api/quiz/attempts/:id/answers` (`{ position, choice, time_ms }`; each question once; returns correct, answer_index, answer_text, evidence) · `POST /api/quiz/attempts/:id/finish` (`{ total_ms }`; every question answered first; returns score, missed questions, previous best).

## Data Model
- `lessons` (id, title, filename, raw_text, word_count, status, error, created_at, source_kind, source_numbers JSON, source_total)
  - `source_numbers[k]` is the real slide / page number (Word: paragraph number) of the k-th block of `raw_text`, `source_kind` is `slide` | `page` | `paragraph` and `source_total` the real count. A slide or page with no text has no block, so a block's place in `raw_text` is not its slide number. NULL on lessons uploaded before migration 005.
- `jobs` (id, lesson_id, stage, status, error, updated_at)
- `sections` (id, lesson_id, position, title, content, simple_version, filipino_version, check_questions JSON, sources JSON)
  - `sources` is the sorted list of slide / page numbers the section was written from. The sections prompt labels each block (`[Slide 3]`) and asks the model for `sources`; in code each number must be a whole number within `source_total` and the number of a block that was in that call's chunk, anything else is dropped and logged, and if nothing is left it is NULL. Original text shows exactly those slides / pages; NULL (older lessons) falls back to a vocabulary match in the client, labelled approximate.
  - `simple_version` stores JSON `{ text, example }`, `filipino_version` stores JSON `{ title, content, check_questions }`; both are made on demand and cached here, the original `content` is never changed.
  - `review_progress.last_section` and `completed_sections` are 0-based indices into the lesson's sections in order.
- `key_points` (id, lesson_id, position, text)
- `key_terms` (id, lesson_id, term, definition, evidence)
- `participants` (id, code UNIQUE, created_at) (migration 008; `P00` made by the migration). Deleting a row cascades to every per-participant table.
- `review_progress` (participant_id, lesson_id, last_section, completed_sections JSON, updated_at), PK (participant_id, lesson_id)
- `flashcards` (id, lesson_id, front, back, state, ease, interval, due_at, reps, lapses, step, kind, evidence, position)
  - `kind` `term` | `concept`; `position` is the new-card order within the lesson. Since migration 008 the scheduling columns here are no longer read: the schedule is per participant in `flashcard_progress`.
- `flashcard_progress` (participant_id, flashcard_id, state, step, ease, interval, due_at, reps, lapses), PK (participant_id, flashcard_id)
  - state 0 new / 1 learning / 2 review / 3 relearning; `interval` in days. No row = the card is new for that participant.
- `flashcard_reviews` (id, participant_id, flashcard_id, rating, reviewed_at, prev_interval, new_interval, state, ease, time_ms, snapshot)
